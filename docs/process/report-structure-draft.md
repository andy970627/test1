## 4. 評審可能問的 5 題與回答要點

1. **問：一般玩家沒戴耳機或用普通手機喇叭玩，聽得出 0.6 秒的節奏盲區嗎？**
   - 答點 1：11/08 第一輪真耳測試已發現此問題，隨即將預告音等關鍵訊號搬移至 200～4000 Hz 中頻區（突出幅度待補）。
   - 答點 2：加入可選視覺輔助（火光隨拍跳動、盲區壓暗、畫面凝結），即使在無聲或嘈雜環境也能清楚判定時機。
2. **問：單元測試 200 多項全綠，為什麼還會出現「不好玩、都在等」的狀況？**
   - 答點 1：單元測試只驗證「程式是否符合規格」，但審議會發現規格本身可能懲罰玩家（例如腳步掩護方向反而讓玩家容易出聲）。
   - 答點 2：團隊改用「程式玩家」模擬按鍵行為量化主動時間比，並搭配 11/09 本機真人真耳試玩，才揭露等待過長與追殺無解的本質問題。
3. **問：為什麼不直接拿現成的電影配樂，而要大費周章用程式動態合成？**
   - 答點 1：現成音檔無法動態將音樂速度、相位與火光及衛兵警戒狀態進行毫秒級的雙向連動。
   - 答點 2：程式合成才能在交接瞬間精準切出 0.6 秒靜止盲區；且架構上規則與聲音分離，未來搬遷至 Unity 時規則邏輯完全不需重寫。
4. **問：AI 代理協作規模這麼大，如何保證程式碼品質不失控？**
   - 答點 1：落實嚴格的驗收審查機制，例如 GitHub Copilot 雲端代理交卷時只要有 14 條測試未過，主對話一律退回。
   - 答點 2：採用獨立多席審議會（不同模型與立場），不採納未經驗證的主觀意見，只採信能透過算式與測試證實的事實。
5. **問：如果 11/11 改版試玩依然不理想，期中報告如何應對？**
   - 答點 1：我們準備了備選方案「雙盲洞穴」，素材現成且風險最低，能立即切回洞穴新進展並將音樂原型作為下一步展望。
   - 答點 2：這正好展示了團隊如何在敏捷開發中透過真實試玩及時止損，並依數據重審核心機制的真實設計決策過程。
