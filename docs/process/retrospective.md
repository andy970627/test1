# 檢討：做得好的與下次可改進的地方

最後更新：2026-11-04

## 做得好的

- **先問再做**：用選擇題確認之後，很少整份重做。
- **用程式量化難度**：
  - 比箭先模擬彈道，才發現原本的數值不可能過關。
  - 乞丐用程式玩家量勝率，「太簡單」變成可以驗證的數字（100% → 0%）。
- **獨立檢查代理有用**：兩次審查都抓到作者自己沒發現的錯。第一次是選單蓋住整個畫面、根本不能玩；第二次是大廳直接走就能贏。
- **規則與畫面分離**：兩個代理能同時改同一個原型，也替之後搬 Unity 鋪好路。

## 下次可改進調整

| # | 問題 | 這次的情況 | 下次怎麼做 |
|---|---|---|---|
| 1 | **架構太晚定** | 第一版原型規則和畫面混寫，第二版才拆開，等於重寫一次 | 第一個原型就先分「規則檔＋畫面檔」，即使是用完就丟的原型 |
| 2 | **自己檢查漏掉明顯的錯** | 第一版發布前，選單蓋住畫面的錯是檢查代理才發現的 | 發布前至少用瀏覽器實際點一次「開始」 |
| 3 | **半成品（WIP）提交** | 為了滿足「有未提交的修改」的自動檢查，在代理還在寫檔時提交了半成品（`7867dcd`、`14bd1f9`） | 代理工作期間用獨立的 git worktree，或約定等代理完成再提交 |
| 4 | **工作程序中斷** | 工作程序重啟了好幾次，中斷後要靠 git 狀態接回進度 | 每個階段開始前先提交；長工作拆小段 |
| 5 | **難度沒在設計時定義** | 「多難算好」直到審查才用勝率衡量 | 設計文件裡就寫目標，例如「直接走過去 ≤30%、用工具 ≥70%」 |
| 6 | **電影內容與「只用《奧德賽》」的規則有張力** | 盲眼豬倌、雅典娜神像相認、阿爾戈斯讓兒子推斷身分，出自電影改編 | **已處理（11/05）**：`CLAUDE.md` 改成電影為主、原典補充、可適度改編，設計文件標出處 |
| 7 | **沒有在真的瀏覽器裡玩過** | 只用無頭瀏覽器跑；滑鼠鎖定、聲音、真實幀率都沒實測 | 請使用者試玩時記下問題，或在有螢幕的環境實測 |
| 8 | **畫面還有已知缺口** | 查看的人會穿過桌子和柱子（沒有尋路）；名字標籤會透過牆顯示 | 正式版要有尋路，標籤要被牆擋住 |
| 9 | **路線分析沒存檔** | 11/02 的「換引擎會不會浪費」只留在對話裡 | 有參考價值的分析一律存進 `docs/` |
| 10 | **代理花費** | 每個代理都要重新讀規格（每個約 15～22 萬 token） | 給代理的說明寫清楚只讀哪幾節；小修改由主對話直接做 |
| 11 | **以為玩家都懂背景** | 冥府靠希臘名字認人、乞丐的知情者靠人物關係，沒看過電影的人會卡住 | 規則寫明「沒看過電影也要懂」；名字加稱號；報告後實作 |
| 12 | **原典內容發展過多** | 使用者決定原典只當背景細節、不做成玩法，網頁連作要整個重做並重選玩法 | 新概念一律先定核心玩法、標出處，原典內容先問再用 |
