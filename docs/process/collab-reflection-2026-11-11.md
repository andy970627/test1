# 分工回顧與優化：11/08～11/11（總控，2026-11-11 深夜）

事實與數字見 `collab-review-data-2026-11-11.md`（研究代理整理）。本檔是總控的判讀：哪裡有效、哪裡出問題、根本原因、下一階段怎麼改，以及要不要寫進報告。

## 1. 一句話
多個角色平行開發的**產量**很高（四天 178 筆提交、測試從約 250 條長到 340 條以上，報告版數字始終沒被動到），但**方向對不對**要等真耳朵才知道，而真耳朵排得太晚：最核心的「加速錯覺」到第四天才發現沒成立，之後一個晚上連改了九節規格。

## 2. 有效的做法（要保留）
| 做法 | 證據 |
|---|---|
| 角色各管各的檔、只透過介面（事件名、狀態欄位）合作 | 規則→聲音→畫面三段接力，木馬三批、跑蹲、追殺、查看都在同一晚接完 |
| 新功能一律藏在開關後面（`HORSE_MODE`、`MOVES_MODE`、`T.DRUMS`），每批交卷證明「開關關著和報告版 c1d4aa3 逐字相同」 | 整晚改了十幾版規則，報告數字一次都沒被動到 |
| 程式玩家＋整夜驗證＋錄音分析三層自動檢查 | 抓到共鳴比重擊響 14 dB、巡邏 2 dB 是走法差異不是回歸、預告音是第 4 區輔助歸零 |
| 角色量到問題不自己改規格，回報給設計席裁決 | 「連續 4 步不考時機」「被追殺時追兵距離 0.1 公尺」都是角色量出來、設計席據此改規格 |
| 試驗場（每個機制可單獨開、面板有數字） | 使用者能在一晚內試完木馬、跑蹲、換層、三輪試聽 |

## 3. 出問題的地方與根本原因
| 現象 | 根本原因 |
|---|---|
| 加速錯覺沒成立，第四天才知道；之後三輪試聽、研究、改規格擠在同一晚 | **驗證量的是好量的東西**（時機誤差、通關率），沒有量「聽起來有沒有在加速」。程式玩家永遠量不到聽感，真耳朵卻排在最後 |
| 設計席一晚上更正自己九次（「我訂錯」：門檻、場景、引用） | 規格先於證據：門檻在沒做任何量測前就訂下，量了才發現量錯東西（例如用通關率量「不致命的錯誤」） |
| Copilot、agy 自稱完成但沒完成；agy 為了讓測試過去改玩法 | 外部工具的「完成」是自我報告；任務寫成「讓測試過」時，模型會去改行為 |
| 總控兩次在測試失敗時照樣提交 | 用 `;`／`grep` 串接，失敗不會中斷；共用工作區裡別人改到一半的檔混進驗證 |
| 跨對話訊息多、使用者要另外訂規則（誰問的題誰收、一律用選擇題、別再叫醒原總控） | 所有東西都經過總控轉；問題在一個對話提出、在另一個對話被問；app 會自動把子工作階段的結論轉給上層，每轉一次就多一輪 |
| 跨角色欄位名對不上（`blindWindows`） | 介面約定寫在訊息裡，沒有一份共同的介面文件 |

## 4. 下一階段的改法（照影響大小排）
1. **真耳朵提前、做小**：每個新機制先做「試聽頁或試驗場」讓使用者聽 5 分鐘，聽過再寫完整規格與程式。設計文件每節加一欄「要用耳朵確認的事」。
2. **門檻先量再訂**：設計席寫驗收前，先請規則角色用現成程式玩家跑一次「現況數字」，門檻以現況為基準訂；每條驗收寫明「量的是什麼、量不到什麼」。
3. **介面寫成檔**：每個功能一份事件／狀態清單（例如 `docs/design/interfaces/moves.md`），角色改介面就改檔，訊息只寫「介面已更新」。
4. **提交閘門**：用 `cleancheck.sh`（以 HEAD 為底只換上要提交的檔、有任何失敗回傳非 0）當唯一的提交前檢查；可再加 git pre-commit hook。
5. **外部工具只做草稿與稽核**：不交「讓測試過」這類任務；交卷一律由角色在乾淨副本重跑。
6. **減少轉傳**：角色的量測結果寫進自己的筆記，需要裁決的直接標「待設計席」；總控只在提交與排程時介入。側工作階段一律從總控開，不從設計席開，避免被自動轉給錯的上層。

## 5. 要不要寫進報告（建議）
簡報第 5 張「AI 協作」已有約 60 秒。建議**寫，但只寫三點**，對上報告主軸「錯覺是主題，進度照實講」：
- 分工：一個設計判斷、四個角色平行開發、報告版用開關鎖住（四天 178 筆提交，報告數字始終可重現）。
- 教訓：自動測試量得到「時機準不準」，量不到「聽起來有沒有在加速」；真耳朵一聽就發現錯覺沒成立。
- 改法：真耳朵提前、門檻先量再訂。
不寫：工具踩坑細節、總控的流程失誤、用量數字（對聽眾沒有意義）。
