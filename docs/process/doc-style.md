# 文件好查的寫法（顏色分配與版面規則）

給所有寫 `docs/` 的人（總控、設計席、角色、報告工作階段）。目標：使用者打開任何一份文件，**10 秒內知道結論、狀態、要不要他做事**。2026-11-14 依使用者要求訂立。

> [!NOTE]
> **用什麼看最好**：GitHub 網頁（repo 已公開，手機也能看）或 Obsidian。兩者都會把下面的「提示框」畫成彩色框。VS Code 用 Ctrl+Shift+V 預覽也行；直接看純文字只會看到 `> [!NOTE]` 字樣，內容不受影響。

---

## 1. 顏色分配：一種顏色只代表一件事

### 1.1 提示框（彩色方框，用在段落）
GitHub 與 Obsidian 都支援的五種，固定用途如下，**不得挪作他用**：

| 寫法 | 顏色 | 只用來放 | 例子 |
|---|---|---|---|
| `> [!IMPORTANT]` | 紫 | **要使用者做的事或決定** | 「請戴耳機聽 g1、g2，回答三選一」 |
| `> [!WARNING]` | 黃 | 風險、已知問題、數字可能不準 | 「躲時新量法只有 +4.1 dB，剛好過門檻」 |
| `> [!CAUTION]` | 紅 | 不可逆、會出事、禁止事項 | 「改寫歷史要強制推送，提交編號全變」 |
| `> [!TIP]` | 綠 | 已驗證可行的做法、捷徑 | 「`?ill=g2` 直接開第二步試聽」 |
| `> [!NOTE]` | 藍 | 背景、出處、補充說明 | 「數字來源：整夜 500 局，96f494e」 |

一份文件裡 `IMPORTANT` 最多一個，放在最上面；要使用者做的事分散在各節就找不到了。

### 1.2 狀態色點（用在標題、表格、清單開頭）

| 標記 | 意思 |
|---|---|
| 🟢 | 已定、已驗證（附提交編號或數字） |
| 🟡 | 待決定（寫清楚誰決定） |
| 🔴 | 卡住（寫清楚卡在誰、卡在什麼） |
| 🔵 | 等真耳朵（要使用者試玩才知道） |
| ⚪ | 擱置、報告後再說 |
| ✅ / ❌ | 測試或驗收的通過／不通過（只用在量測結果） |

聊天標題用的色塊（🟥🟧🟨🟩🟦＝距截止日幾週）**不要用在文件裡**，免得兩套顏色混在一起。

### 1.3 出處標籤沿用專案規則
【經典】【電影】【原典】【改編】，見 `CLAUDE.md` 的「內容限制」。

## 2. 每份文件的開頭（固定順序）

```markdown
# 主題（日期，作者角色）

> [!IMPORTANT]
> 要你做的事：……（沒有就整個框省略）

狀態：🟡 待設計席裁決第 4 節。
一句話結論：……
依據：檔案路徑、提交編號。
專有詞：詞＝白話解釋（第一次出現的都要）。
```

- **結論放第一節**，細節往後放。讀者只讀第一節也不會誤會。
- 狀態改了就改這一行，不要在文末追加「更新：……」讓人從頭找。

## 3. 內文

- 標題用編號（`## 3.`、`### 3.2`），對話裡才能說「看第 3.2 節」。
- 比較選項一律用表格，欄位固定：做法／好處／代價／改回來的難度。
- 數字一定附來源（提交編號、指令、局數）；沒量過的寫「推測」。
- 一段只講一件事；超過 5 行就拆清單。
- 檔名：`YYYY-MM-DD-主題.md`；草稿加 `-draft`，定稿刪掉草稿或在草稿開頭指向定稿。

## 4. 好查的入口

- 設計：`docs/design/concepts-overview.md`（概念總覽）、`glossary.md`（術語表）。
- 過程：`docs/process/README.md`、`production-log.md`。
- 新文件寫完，在對應的總覽或 README 加一行連結，附狀態色點。
