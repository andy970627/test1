# 架構審查、製作路線比較與四角色分工回顧（2026-11-14，總控）

> [!IMPORTANT]
> 要你決定兩件事（第 5 節）：一、往後走哪條製作路線；二、四個角色要不要調整。

狀態：🟡 等使用者選路線與分工調整。
一句話結論：**留在網頁（純 JS＋Web Audio）最合適，Unity 洞穴專案封存當另一章素材；換引擎前先整理三處技術債。四個角色寫程式不打架，缺的是「量測算不算數」有人負責。**
依據：三份子代理盤點（架構、引擎研究、分工數據），總控抽查行數、Unity 最後提交、角色提交數皆相符；`node --test` 348 項全過（約 58 秒）。
專有詞：**UMD**＝同一個 .js 檔在瀏覽器和 Node 都能載入的寫法；**無頭測試**＝不開畫面、不開瀏覽器，在終端機直接跑規則的自動測試；**Web 匯出**＝引擎把遊戲轉成網頁版；**延遲**＝按下鍵到聽到聲音之間的時間差，節奏判定窗只有數十毫秒，延遲不穩就會判錯。

## 2. 製作路線比較

| | A 留在網頁（建議） | B Unity 6 | C Godot 4 |
|---|---|---|---|
| 做法 | 現有 JS＋Web Audio 繼續；要 3D 再加 Three.js 或 Babylon.js | 把 risset.js 翻成 C#、聲音全部重做，洞穴玩法另成一章 | 規則全部重寫成 GDScript（C# 不能匯出網頁），聲音重做 |
| 音訊時序 | 自己掌控音訊時鐘，最準；手機延遲要做校準 | **Web 版只剩基本音訊**，混音器只能調音量，FMOD 在 Web 不能用 | 低延遲模式缺效果器與 3D 定位，完整模式延遲變大；論壇有 Web 版音樂不同步回報 |
| 網址試玩 | 最輕，任何靜態主機 | 可行但檔案大，iOS 有記憶體閃退回報（未證實） | 可行，比 Unity 輕 |
| AI 寫程式與自動測試 | 最容易，348 項已在跑 | 要開編輯器，無頭測試要自建 | 純文字檔友善，但 Web 音訊仍要在瀏覽器驗證 |
| 費用 | 免費 | Personal 免費（營收 20 萬美元以下） | 免費 |
| 上架原生 App | 要另外包裝（Capacitor 之類，未查證） | 最成熟 | 成熟 |
| 改回來的難度 | 規則與測試都能當之後換引擎的規格 | 換過去後網頁版停擺，回頭要重接 | 同 B |

結論：這個遊戲的核心是**聲音時序**，而 Unity 與 Godot 的網頁版恰好都在音訊上打折扣。除非要上架手機 App 或主機，否則換引擎只會付出重寫成本、換到更差的音訊。
來源：Unity 6 Web 音訊文件 <https://docs.unity3d.com/6/Documentation/Manual/webgl-audio.html>、Godot 4.6 Web 匯出文件 <https://docs.godotengine.org/en/4.6/tutorials/export/exporting_for_web.html>、web.dev 音訊輸出延遲 <https://web.dev/articles/audio-output-latency>。節奏遊戲網頁實例未查到。

> [!TIP]
> 不論選哪條，先做這三件，之後換引擎也省事：
> 1. 規則和聲音共用的常數抽成單一資料檔。
> 2. `index.html` 拆成輸入、畫面、遊戲迴圈三個檔。
> 3. 亂數、導覽、遙測收進 `prototypes/shared/`。

## 3. 四角色分工回顧（11/11 之後）

| 角色 | 提交數 | 主要檔案 | 11/12 起 |
|---|---|---|---|
| 規則 | 24 | risset.js、程式玩家 | 3 筆 |
| 聲音 | 21 | audio.js | 4 筆 |
| 畫面 | 21 | index.html、試驗場 | **0 筆** |
| 錄音與工具 | 13 | 錄音分析、遙測 | 3 筆，**解開最難的問題** |

來源：`git log --grep="（X角色）"`；全 repo 481 筆提交中只有 79 筆帶角色標記，其餘是設計席、總控、報告與外部代理。

**分得好的地方** 🟢
- 檔案幾乎不重疊：只有程式玩家、試聽頁、一份設計文件被兩個角色同時動過，沒有合併衝突。
- 11/11 回顧的結論沒有被推翻；「驗證量的是好量的東西」「門檻先量再訂」又被證實一次。

**分得不好的地方** 🔴
1. **量測算不算數沒人負責**。11/12 晚上「踩得上的拍突出量」：聲音角色試了四種改法都不過，29 分鐘後錄音工具角色才發現是量法錯，同一份錄音新舊量法差 6 dB 以上。門檻由設計席訂、量法由工具寫、改動由規則和聲音做，三方都只管自己那段。
2. **量測過了，耳朵不認**。新量法全過，使用者 11/14 試聽仍說「速度不夠快所以都很明顯」。
3. **一個功能要跨三個角色接力**（新鼓聲第二步：聲音→規則→工具），畫面角色同時閒置。
4. **衛兵聲音沒寫進事件紀錄**，量測抓不到，約 270 個不明起音查不出來源，落在角色之間的縫。
5. 角色工作階段沒記用量，無法比較哪個角色划算。

## 4. 建議

| 問題 | 建議做法 | 代價 |
|---|---|---|
| 量測沒人負責 | 錄音與工具角色正式改名**「量測與驗收」**，有權要求重量；改任何聽感數字前先請它確認量法 | 幾乎沒有 |
| 量過耳朵不認 | 每條驗收寫「量的是什麼、量不到什麼」；聽感類改動**先給使用者聽再量** | 要多等使用者 |
| 畫面閒置 | 畫面角色改成**有需要才開**，不常駐 | 開新工作階段要重讀筆記 |
| 跨角色接力 | 暫不改成依功能切（證據只有一例，且每個角色要懂全部程式，上下文更快滿） | — |
| 用量不明 | 角色每輪結束在筆記記一行用量 | 很小 |
