# 哪些分工做法該升級成全域規則（2026-11-09 提案）

來源：專案 `CLAUDE.md`（11/09 版）、`ai-collaboration.md` 第 7～13 節、`local-handoff.md`、`retrospective.md` 第 13～17 項、`approvals.md`、`agent-notes/README.md`；對照本機 `~/.claude/CLAUDE.md`（11/09 讀取版）。

**結論**：40 條做法，**全域 27 條**（其中 #14 併入 #13）、**專案 7 條**、**待觀察 6 條**。草案 **34 行**（改既有 6 行、新增一節 28 行）。專案和全域、全域自己內部的**衝突 8 處**。
全域規則只有本機能改。這份只是提案，使用者選好要套哪幾段才改 `~/.claude/CLAUDE.md`，改完重跑 `~/.claude/cloud-sync/build.py`。

判準：
- **全域**：任何有遠端 git、會同時用本機與雲端（或多個工作階段、多個代理）的專案都適用，不用改字就成立。
- **專案**：綁 Unity、真耳朵、錄音分析、試玩頁、這個 repo 的路徑或角色。
- **待觀察**：才剛開始試，或還沒有數字證明有效。11/10～11/16 試一週後再決定。

## 二、全域規則草案（可直接貼進 `~/.claude/CLAUDE.md`，34 行）

### A. 改既有段落（6 行）

放在「Git 雲端同步」最後（新增 3 行）：
```
- **換手**：同一時間一條分支只給一邊（本機、雲端或一個工作階段）改；換手前先推、接手前先拉。本機工具產生或改動的檔（編輯器場景、設定、資產）也要提交推上去，另一邊才看得到。
- **只有主對話提交推送**：子代理與同分支的副工作階段不提交、不推送，只改自己負責的檔，改完回報主對話。
- **合併**：到 main 的合併由使用者按；雲端負責把 CI 弄綠並提醒。CI 很重的專案加路徑過濾，只改文件不跑全套。
```

改「Copilot 雲端代理」第 9 條（原「合併由使用者決定，Claude 不合併」，和下一條矛盾）：
```
- **產出一律當未審核草稿**：照委派規則逐項審 PR，結果留言在 PR 上；合併到工作分支依下一條，到 main 由使用者按。
```

改「模型選擇」的「子代理」與「節流」兩條：
```
- **子代理**：開發代理 Opus；彙整、搜尋比較、照腳本跑的稽核用 Sonnet，要自己寫算式推翻設計的稽核用 Opus；審議席、初稿、翻譯、整理清單優先丟 agy（Claude 只審）；自足、能寫驗收標準的程式任務先問要不要派 Copilot。
- **節流**：5 小時窗超過 80%（本機 `get_usage` 可讀，雲端讀不到、請使用者提醒）時，不急的子代理工作改派 agy、Copilot 或等重置；主對話上下文超過一半或出現下方「交接時機」訊號就寫交接文件。
```

### B. 新增一節（28 行）

放在「委派規則」之後：
```
## 本機與雲端、多工作階段協作（使用者 2026-11-09 自 test1 升級）
### 分工與交接
- 本機和雲端只透過 git 分支交接檔案與結論；對話記憶不跨邊。
- 雲端做不需要本機硬體、帳號或真人判斷的事（規則與程式、測試、CI、文件、PR）；本機做要硬體、桌面程式、帳號金鑰、真人感受判斷的事，以及合併。
- 需要本機時用任務卡交接，寫明分支、提交與要做什麼；建不了卡就請使用者自己開本機對話。
- 本機 ↔ 雲端訊息雙向可通：本機 `SendMessage` 直接送；雲端回傳第一次要使用者在信任裝置核准（不可逆，之後該雲端工作階段只限信任裝置），送核准卡前先說明。
- `ListAgents` 只列對話標題、不列 `session_…` ID，同題對話可能不只一個：任務卡與交接文件寫對話標題（加分支名），送出前核對對象。
- 本機推了雲端在等的東西，推完順手 `SendMessage` 一句：推了什麼、哪個提交。
- 能不能通、能不能用，以兩邊實際收到、跑通為準，不只看一邊的工具說明。
### 結論入檔與交接文件
- 代理報告、分析、決定一回來就把結論寫進 repo 文件，不靠對話記憶（工作程序重啟會丟報告）。
- 交接文件時機：對話被壓縮、工作程序重啟 2 次以上、要換手（本機↔雲端、換模型）、一輪收工、用量超過 80%、開始重問已決定的事或語言跑掉。剛開一輪、代理還在跑、十分鐘內剛寫過就不寫。
- 交接文件只寫現況、下一步、待決定、去哪找、建議技能；細節指檔案不重抄；不含金鑰與個資；有遠端的專案另抄一份進 repo（如 `docs/process/handoff/<日期>.md`）。
### 人工核准
- 必須人工核准：合併 main、刪分支、上傳與發布、授權與金鑰、花錢的派工、公開分享連結、L3 設計抉擇、要真人感受的判斷。
- 子代理與副工作階段遇到上面任一項：不自己做、也不卡住等人，寫進專案的待核准清單（預設 `docs/process/approvals.md`：日期｜事項｜理由｜怎麼按｜提出者）再回報；主對話一次整理成選擇題，按完移到「已處理」。
### Claude 子代理
- 派之前先問三題，任一為「是」才派：兩個以上檔案能分開並行？要先讀約 300 行以上的規格或程式？需要獨立的眼睛（審查、稽核、審議）？三個都否就主對話自己做；子代理底價約 10～15 萬 token。
- 任務說明列明只讀哪些檔、哪幾節；多個代理共用的介面約定寫成一個小檔讓大家讀同一份。
- 同一輪的追加修正直接傳訊息給原代理續用，最多 2～3 次，之後新開。
- 跨輪、跨重啟用角色筆記（`docs/process/agent-notes/<角色>.md`，300 行內：結構與入口、介面約定、陷阱、驗證方式、上次做到哪）；角色每輪結束更新、主對話審；上下文太長就關掉重開、讀筆記接手。
- 不用「分身」型代理（複製整段對話）來省讀檔，它比新代理貴。
- 子代理回報的數字、統計與「已驗證」一樣當草稿，主對話自己核對（委派規則 3 延伸到 Claude 子代理）。
- 「測試都過但感覺不對」先派稽核（只讀、只算，便宜又有數字），看不出再開審議；審議刻意混模型，裁判只採信能查證、自己算過的主張。
### 其他
- agy 實測限制：`-p` 讀不到 stdin、命令列塞不下長文件，題目檔放資料夾用 `--add-dir` 讓它自己讀；題目寫明「不要用其他工具」；要記用量加 `--output-format json`（一次底價約 2.6 萬 token，不吃 Claude 額度）。
- 用繁體中文的專案：自動觸發的回合（提醒、代理完成通知、重啟接續）第一句先用中文寫結論；給代理的任務說明開頭、結尾都寫「最終報告用繁體中文」。
- 專案 `CLAUDE.md` 每個對話與代理都會讀：只放摘要，細節移到文件再指過去。
```

行數：A 段 6 行（Git 3、Copilot 1、模型 2），B 段 28 行（標題與小標 6、規則 22），合計 34 行。
