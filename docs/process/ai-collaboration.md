# AI 協作與分工介紹

## 1. 角色

| 角色 | 是誰 | 負責 | 不做 |
|---|---|---|---|
| **製作人／設計決策** | 使用者 | 定方向、選方案、試玩、回饋 | — |
| **主對話（協調者）** | Claude Code 主對話 | 拆工作、寫給代理的任務說明、整合結果、跑測試、提交與推送、發布網頁、更新文件、向使用者報告 | 不在代理工作時改同一個檔案 |
| **開發代理** | Claude 子代理，每次一個任務 | 只改指定的檔案：規則模組＋測試，或畫面層，或一個原型 | 不提交、不推送、不碰別人的檔案 |
| **檢查代理** | 獨立的 Claude 子代理 | 用瀏覽器（Playwright）實際打開原型、程式化試玩、截圖，對照設計文件列出問題 | 不改任何檔案，只回報 |

## 2. 工作規則（寫在 `CLAUDE.md`，每個新對話都會讀到）

1. **不確定先提問**：用選擇題問，附建議選項；有慣例可循的就直接決定。
2. **快要難以移植時先停下來**：說明會綁住什麼、移植要重做多少，讓使用者選。
3. **代理分工**：各部分交給代理；主對話負責整合、提交、報告。
4. **內容限制**：所有內容出自《奧德賽》（含使用者指定參考的電影改編），不出現現代元素。
5. **發想登記**：主線以外的概念都登記在 `docs/design/concepts-overview.md`。

## 3. 一輪的流程

```
使用者提出需求
  → 主對話：不確定的地方用選擇題問清楚
  → 主對話：先把設計寫進文件（設計先於程式）
  → 主對話：提交目前進度，當作代理的共同起點
  → 開發代理 ×N 同時進行（每個只改自己的檔案）
  → 主對話：收報告、轉告相關代理（例如規則新增了欄位）、跑測試、提交
  → 檢查代理：實際打開、試玩、對照設計
  → 修正代理 ×N
  → 主對話：測試、提交、發布、向使用者報告
```

## 4. 為什麼「規則」和「畫面」分開

- **規則檔**：純邏輯，不碰畫面、聲音、輸入裝置，例如 `sim.js`、`rules.js`。
  - 可以用 Node 直接測試，也可以寫「程式玩家」驗證關卡能不能過、會不會太簡單。
  - 之後搬 Unity，只要翻成 C#，對應主線的 `Odyssey.Core`。
- **畫面檔**：每幀把輸入交給規則，再照規則的狀態畫出來，例如 `index.html`。
- **分工上的好處**：規則代理和畫面代理可以同時工作，只要事先講好兩邊的介面。

## 7. 分工路線比較（11/08，依這兩週實際用過的做法）

| 路線 | 怎麼做 | 用在 | 優點 | 缺點 | 實測數字 |
|---|---|---|---|---|---|
| **A. 單一對話迭代** | 一個對話從頭做到尾，使用者回饋就改 | 主線《雙盲洞穴》前期、小修（按鍵配置） | 脈絡完整、不用寫任務說明、小改最快 | 一次只能做一件事；上下文累積後容易出錯、變英文；沒有獨立檢查 | 洞穴 20 多輪回饋；按鍵配置從決定到推送 10 分鐘 |
| **B. 主對話＋開發代理（照檔案切）** | 主對話寫介面約定，規則、聲音、畫面各一個代理同時改各自的檔，主對話整合、測試、提交 | 木馬之夜每一輪、返回主畫面、稽核修正 | 三倍並行；檔案不互踩；規則與畫面分離本來就是為了這個 | 介面要先寫清楚（約定檔）；代理各讀一遍規格很貴；一個代理晚到，其他要等 | 稽核修正三代理各 19～23 萬 token、11～14 分鐘同時跑完；比序列省約 2/3 時間 |
| **C. 開發 → 檢查 → 修正三段** | 開發代理做完，獨立的檢查代理實際打開玩、對照設計列問題，再派修正代理 | 乞丐與比箭 11/04、網頁連作 11/05 | 抓到作者看不到的錯（選單蓋住畫面、大廳直走就贏） | 多一輪時間；檢查代理要能「真的玩」（Playwright、錄音工具） | 兩次檢查各抓到 3～9 個會擋住的錯 |
| **D. 審議會（多席獨立＋裁判）** | 同一題給 N 席各自盲答（不同立場或不同模型），裁判只採信能查證的主張 | 木馬之夜設計審視 11/07 | 找出「測試過了但設計壞了」的問題；分歧本身就是資訊 | 貴（五席 12～14 萬 token 各一份）；同一家模型共用盲點；裁判要自己動手算，不然只是投票 | 五席「最該先改」選了四件不同的事；裁判算出腳步掩護方向反了，五席只有一席真的算過 |
| **E. 稽核代理（只讀、只算、只錄）** | 一個代理不改檔，用 Node 把公式全部算一遍、跑錄音工具，列錯誤清單 | Risset 層稽核 11/07 | 比審議便宜、比測試深；產出直接是修正清單 | 只看得到「有沒有照原理做」，看不到「好不好玩」 | 22 萬 token，15 個錯，其中 2 個聽得出來 |
| **F. 搜尋比較代理** | 一個代理上網查、寫比較表 | 音效工具比較 11/07 | 主對話不用自己翻幾十個網頁 | 數字要再確認（授權門檻抓不到官網原文） | 16 萬 token、25 次搜尋、55 條來源 |
| **G. 雲端／本機分工** | 雲端做「對不對」（規則、測試、錄音分析），本機做「好不好」（真耳朵、Unity、錄影）；只靠 git 分支交接，用任務卡片開本機對話 | 11/07 起 | 各做各擅長的；本機的試玩紀錄直接變雲端的需求 | 來回一次至少半天；喇叭聽不出來這種事雲端量不到，要本機先說 | 第一輪試玩三項聽不出 → 雲端改成 8 項可量的檢查 |
| **H. 多代理工作流（Workflow）** | 用腳本把 N 個代理排成管線，自動分支 | 還沒用 | 可大量並行、可重跑 | 要使用者明確同意；這個專案的規模還不需要 | — |

**什麼事用哪條**
- 小修、文件對齊、提交：A。
- 一輪功能開發（兩個檔以上同時改）：B，必要時接 C。
- 「測試都過了但感覺不對」：先 E（便宜、有數字），數字看不出再 D。
- 要查外部現況：F。
- 任何「好不好聽、好不好玩」：G，雲端不要猜。
- 一輪完整流程的建議順序：設計文件 → B 開發 → E 稽核或 C 檢查 → 修正 → G 本機試玩 → 回到設計文件。

**代理用量的經驗值**（這個專案）
- 讀完規格再動手的開發代理：15～23 萬 token；只讀不改的稽核、審議席：12～22 萬。
- 最貴的不是代理本身，是「每個代理都重讀一次規格」。給代理的說明寫明只讀哪幾節、把介面約定寫成一個小檔讓大家讀同一份，比省模型更有效。
- 主對話的上下文會被代理報告塞滿，所以代理報告的結論要立刻寫進 `docs/`（重啟時曾丟過兩份報告，見檢討第 17 項）。

## 8. 模型選擇（11/08）

這個工作階段的主對話跑 Claude Fable；子代理不指定時沿用主對話的模型，可以指定 Opus、Sonnet、Haiku。

| 角色 | 建議模型 | 理由 |
|---|---|---|
| 主對話（拆工作、寫約定、整合、提交、和使用者對話） | 最強的那一個（目前 Fable） | 脈絡最長、決定最多；錯一個決定比省一點錢貴 |
| 開發代理（規則、聲音、畫面） | 沿用主對話 | 要讀懂規格、寫測試、自己驗證；省不得 |
| 檢查、稽核代理 | 沿用主對話 | 要自己算、自己跑工具；弱模型會「看起來查了」 |
| 審議席 | **刻意混用**：主對話模型的不同立場 ＋ Opus ＋ Sonnet 各一席 | 同一家模型共用盲點，換模型是最便宜的「換腦袋」。11/07 五席裡 Opus 席提出「盲區被稀釋」、Sonnet 席提出「盲區加寬」，都是 Fable 三席沒提的角度 |
| 搜尋比較、文件翻譯、整理清單 | Sonnet 或 Haiku | 工作明確、靠工具不靠推理；Haiku 適合「把 N 份文件的英文找出來」這種機械活 |
| 程式玩家、數值模擬 | 不用模型，寫成 Node 腳本 | 模擬一次幾秒、可重跑；比叫代理「估一下」準 |
| 外部模型 | **11/08 本機確認**：透過 Antigravity CLI（`~/.gemini/bin/agy.exe`，`agy models`）可用的模型有 `gemini-3.8-flash-high／medium／low`、`claude-sonnet-4-6`、`claude-opus-4-6-thinking`、`gpt-oss-120b-medium`；GitHub Copilot 雲端代理（`gh agent-task create -R … -F 簡報.md --base 分支`，本機沒有問答版 CLI）可以當審議席：簡報裡寫明只讀哪幾個檔、答案寫成獨立新檔、不讀其他席，它會自己開分支與 PR（11/08 第一次用，PR andy970627/test1#8，丁席）；交卷後 Claude 審驗收標準，通過就把它的分支合併進目前的工作分支並推送，再關 PR、刪分支；需要主對話判斷的才先確認（使用者 11/08 晚間改定，取代同日稍早「審完照貼、關掉不合併」；PR #8 是舊規則下關的，原文已照貼，不再補合併）。11/08 審議席：`gemini-3.8-flash-high`（甲）、`gpt-oss-120b-medium`（乙）、Claude Opus 懷疑者（丙）、Copilot 雲端代理（丁） | 用途（使用者決定）：審議席、搜尋比較與文件翻譯等機械活；不當開發代理（沒有這個工作階段的工具，只能給文字任務再貼回結果）。實測限制（11/08）：列印模式 `-p` 讀不到 stdin、命令列長度塞不下整份規格，要用 `--add-dir <資料夾>` 把題目檔放進工作區讓它自己讀；題目裡要寫明「不要用其他工具」，否則 gpt-oss 連算術題都會去叫指令、在 headless 下被擋成空白回答。第一次用在《大廳復仇》合成版規格審議，原文見 `docs/design/2026-11-08-vengeance-v2-council.md` |

**原則**：主幹用最強模型、把錢花在「決定」上；平行的機械活降級；審議刻意混模型（含外部模型）；能用腳本算的不要用模型猜。

**11/08 補充（使用者決定，寫在全域規則「模型選擇」）**：Claude 是唯一會用完的額度，外部訂閱 11/08 才接上、吃月費用不完。任務卡開新工作階段一律指定模型：預設 Opus，只讀／驗證用 Sonnet，只有 L3 設計抉擇用 Fable；審議席、初稿、翻譯優先丟 agy；自足的程式任務先問要不要派 Copilot。本機逐字稿彙整（`~/.claude/orchestration/usage-report.py`）：11/03～11/08 每天 6～11M token 幾乎全是 Opus，Sonnet 一天不到 1M，這就是要改的現況。

**外部模型進審議會的做法**：同一份題目與檔案清單給外部模型一份（它讀不到這個工作樹，所以題目裡要貼上需要的文件段落），答案存進 `docs/design/` 的審議文件附錄，裁判一樣只採信能查證的主張，並在報告裡註明是哪個模型。

## 9. 代理發派的門檻（11/08，為了控制 Claude 用量）

### 9.1 這兩天的實際花費（子代理 token，從完成通知抄的）
| 類型 | 件數 | 每件 | 小計 | 值不值 |
|---|---|---|---|---|
| 開發代理（規則／聲音／畫面，讀規格＋寫＋驗證） | 7 | 19～27 萬 | 約 160 萬 | 值：三個同時跑省 2/3 時間，產出都進了程式 |
| 設計規格代理（A、B、合成版、核心總綱、診斷） | 5 | 15～23 萬 | 約 95 萬 | 值：使用者要「文件寫透再實作」，這是主產出 |
| 審議席（五席 Claude） | 5 | 12～14 萬 | 約 65 萬 | 半值：抓到關鍵問題的是裁判自己算的那一題；之後審議改用外部模型（本機四席只花 Claude 一席） |
| 稽核、工具比較、專家視角、術語表（只讀＋查＋寫） | 4 | 16～28 萬 | 約 90 萬 | 稽核值；專家視角 28 萬（67 次工具）偏貴，可用 Sonnet；術語表已用 Sonnet |
| 檢查與修正（返回主畫面 3 件、喇叭可聽度 1 件） | 4 | 12～27 萬 | 約 75 萬 | 值 |
| **合計** | 25 | — | **約 480 萬** | 主對話自己的上下文另計，且每次代理報告都灌進主對話 |

兩個觀察：
1. **一個代理的底價約 12～15 萬 token**，不管任務多小——因為它要重讀規格、`CLAUDE.md`、相關檔案。所以「小事派代理」是最浪費的。
2. **主對話做小事的成本是上下文變長**，不是 token 數本身；但上下文一長就容易出錯、變英文、需要重啟。所以小事也不是無限制留給主對話。

### 9.2 門檻：什麼時候派、派給誰
先問三個問題，任一為「是」才考慮派代理：
1. **要同時改兩個以上的檔案、而且彼此可以分開做**？（並行才有省時間的價值）
2. **要讀超過約 300 行的規格或程式才能動手**？（主對話讀進來會吃掉自己的上下文，不如讓代理讀）
3. **需要獨立的眼睛**？（審查、稽核、審議——作者自己看不到自己的錯）

三個都「否」→ 主對話自己做。例子：改一個常數、補一段文件、修一個提示文字、對齊數字、回答問題、看 CI、提交。今天這類事主對話都自己做了（返回主畫面的 README 補漏、審議裁判總結、術語表的 L1～L3、82% 釐清）。

| 情況 | 派給誰 | 理由 |
|---|---|---|
| 改一個檔、不到 50 行、不用新讀規格 | 主對話 | 代理底價 12 萬，不划算 |
| 文件翻譯、整理清單、搜尋比較、術語表 | **Sonnet** 子代理（或外部模型） | 機械活，不需要判斷；今天術語表 24 萬若用 Opus 會更貴 |
| 只讀不改的稽核、數字核對 | Sonnet，除非要自己寫算式推翻設計 → Opus | 稽核要「算」，Opus 懷疑者席算出按住右鍵無敵，Sonnet 席沒算 |
| 開發（規則、聲音、畫面各一檔以上） | Opus，照檔案切、同時跑 | 要讀懂規格、寫測試、自己驗證 |
| 設計規格（一份完整文件） | Opus | 要判斷取捨 |
| 審議席 | **外部模型優先**（agy：Gemini、GPT-OSS；Copilot），Claude 最多一席懷疑者 | 11/08 本機四席只用 Claude 一席，結果比 11/07 五席 Claude 更有用 |

| 工作流（Workflow）大量並行 | 暫不用 | 規模還不需要，且要使用者明確同意 |

### 9.3 省用量的做法（已採用的打勾）

- [x] 任務說明寫明「只讀哪幾節」。
- [x] 代理報告一回來就把結論寫進 `docs/`，主對話不靠記憶。
- [x] 審議改外部模型。
- [x] 程式玩家、數值模擬寫成 Node 腳本，不叫代理「估一下」。
- [ ] **同一輪不要派超過 3～4 個代理**：今天一度 4 個設計代理＋1 個同時跑，報告一起回來把主對話灌滿，重啟了兩次。改成一輪最多 3 個，回來消化完再派下一批。

- [ ] 代理報告要求「結論先、三百字內、細節寫進檔案」，減少灌進主對話的量（今天的報告平均一千字以上）。

### 9.5 子代理能不能持續用，省掉每次重讀？（11/08）

**可以，有兩種方式，各有限制。**

| 方式 | 怎麼做 | 省什麼 | 限制 |
|---|---|---|---|
| **續用同一個代理** | 代理完成後主對話用「傳訊息」再派下一件事，它帶著原本讀過的規格、改過的檔的記憶接著做。今天稽核修正那輪就是這樣：規則代理做完介面後，聲音與畫面代理被追加訊息「介面已就緒、注意這幾處差異」，不用重讀 | 不用重讀規格（省約 10～15 萬 token 的底價）、不用重新理解檔案 | (1) **容器一重啟就斷**：今天容器重啟了三次，重啟前的代理只能讀它留下的紀錄檔，不能再傳訊息。(2) 它的上下文會一直長，第 3、4 件事之後比新開一個還貴、也更容易出錯；每一輪仍要送整份累積的上下文（有快取會便宜一些）。(3) 一次只能做一件事，並行還是要多個代理 |
| **角色筆記檔** | 每個角色（規則、聲音、畫面、錄音工具）維護一份兩三百行的筆記 `docs/process/agent-notes/<角色>.md`：檔案結構、介面、常數位置、常見陷阱、上次做到哪。新代理先讀筆記再動手，不用從頭讀 1100 行的規則檔 | 把「讀規格」從 15 萬壓到約 2 萬；重啟也不怕 | 筆記要有人維護（代理做完順手更新，主對話審）；筆記寫錯會誤導 |

**建議的用法**
1. **同一輪之內**續用：一個代理負責一個檔，一輪裡的追加修正直接傳訊息給它，最多 2～3 次。
2. **跨輪、跨重啟**用角色筆記：每輪結束要求代理把「下次要知道的事」更新進筆記，字數上限 300 行。
3. 介面約定檔、「只讀哪幾節」的指示照舊，這兩個和筆記合起來，一個開發代理的起步成本可從 15～20 萬降到 5 萬以內。
4. 不要用「分身」型代理（複製主對話全部上下文）來省讀檔：它比新代理更貴。

**今天就能開始**：下一輪派代理時，任務說明最後加一條「做完把你學到的檔案結構、陷阱、未完成事項更新到 `docs/process/agent-notes/<角色>.md`（沒有就新建，300 行內）」。

## 10. 交接文件（handoff）的時機（11/08）

`anthropic-skills:handoff` 技能會把現況、下一步、去哪找寫成一份交接文件，讓新對話不用重讀整段歷史。它本身存到暫存目錄；這個專案另外抄一份到 `docs/process/handoff/<日期>.md`，因為雲端與本機只靠 git 交接。

**什麼時候該寫（偵測訊號）**
| 訊號 | 怎麼看出來 | 動作 |
|---|---|---|
| 對話被壓縮過（出現「摘要」接續） | 回覆開頭引用「上一段摘要」 | 下一個段落結束就寫 |
| 工作程序或容器重啟 ≥ 2 次 | 系統提示「工作程序已重啟」 | 立刻寫，否則下一次重啟可能丟代理報告 |
| 要換手（雲端 ↔ 本機、換模型、換人） | 使用者說要本機試玩、要錄影、要開新對話 | 寫，並建任務卡 |
| 一輪結束、所有代理收工 | 沒有進行中的代理、已提交推送 | 順手寫（成本最低的時機） |
| 用量接近上限 | 全域規則：5 小時窗 > 80%（本機 `get_usage`）；雲端由使用者提醒 | 寫完再停 |
| 主對話開始重複問已決定的事、或回覆變英文 | 自己察覺或使用者指出 | 上下文已太長，寫完開新對話 |

**不要寫的時候**：剛開始一輪、代理還在跑（結論未定）、十分鐘內剛寫過。

**內容規矩**：只寫現況、下一步、待決定、去哪找；細節指檔案不重抄；不含金鑰與個資；列「建議的技能」。

## 11. 儲存庫大小、用量，要不要把音樂原型拆成獨立 repo（11/09）

**量到的數字**：被 git 追蹤的內容不大——Unity 專案 `Assets/` 13 MB（404 檔）、`prototypes/` 1.3 MB（32 檔）、`docs/` 1.2 MB（55 檔）、`tools/` 追蹤的只有 304 KB（錄音輸出 827 MB 沒進 git）；`.git` 27 MB。`CLAUDE.md` 7,740 字元。

**結論：repo 大小不吃 token，拆 repo 現在不划算；真正在浪費的是 CI 分鐘，已修。**

| 會不會多耗用量 | 說明 |
|---|---|
| repo 裡有很多檔 → **不會** | token 只算「讀進對話的東西」。主對話和代理只讀被指到的檔；Unity 的 404 個檔沒人讀就是 0。 |
| `CLAUDE.md` 每個對話與代理都讀 → **會，約 4 千 token 一次** | 一天 25 個代理就是 10 萬。可以把「雲端與本地分工」的細節搬去 `local-handoff.md` 只留摘要，省三分之一。 |
| 代理「到處找」→ **會** | 任務說明沒指定檔案時，代理會 grep 整個 repo，Unity 資料夾會跑進結果。已有的做法：任務說明列明只讀哪幾個檔、哪幾節。 |
| **CI 每次推送都跑 Unity → 不是 token，是 Actions 分鐘** | 11/08 的 31 個提交有 24 個只改 `docs/`，每個都觸發 Unity 測試＋網頁版建置＋畫面測試，約 25 分鐘；一天燒掉約 10 小時 Actions。11/09 加了路徑過濾：只改 docs 什麼都不跑；改網頁原型只跑 Node 測試（30 秒）；改 Unity 才跑全套；推到 main 一律全跑。 |

**拆成獨立 repo 的得失**
- 得：clone 小一點（27 MB → 幾 MB）、grep 乾淨、CI 設定單純。
- 失：規則（`CLAUDE.md`）、技能、Stop 檢查、CI、交接文件要維護兩份；連作首頁要連到主線洞穴的網頁版（`odyssey-series/cave/`），拆開後要跨 repo 取成品；報告要同時講洞穴與音樂原型，素材分兩處；git 分支交接流程多一倍。
- 判斷：音樂原型和主線在**內容**上確實不互相影響，但在**流程**上共用的東西（規則、技能、CI、交接、報告）比共用的程式多。等報告後若音樂原型確定變成獨立產品再拆，那時用 `git subtree split` 把 `prototypes/`＋`docs/design/` 的歷史帶走，不用現在決定。

**現在就做的省法**（比拆 repo 便宜）
1. CI 路徑過濾（已做）。
2. 代理任務說明一律列檔案清單（已做）＋角色筆記檔（9.5 節，下一輪開始）。
3. `CLAUDE.md` 瘦身：雲端與本地分工細節移到 `local-handoff.md`（待使用者同意）。
4. 錄音輸出 `tools/playtest-recorder/out/` 保持不進 git（已在 `.gitignore`）。

## 12. 雲端與本機的協作能力差別，以及整個分工架構（11/09）

### 12.1 能力對照（以 11/09 實測與工具說明為準）

| 能力 | 雲端工作階段 | 本機工作階段（Windows 桌面版） |
|---|---|---|
| 子代理（同一工作階段內） | 有。可指定模型；做完可再傳訊息續用（9.5 節）；容器重啟就斷 | 有，同樣可續用；程序開著就不斷（**11/09 實測**：追加一件不用重讀檔案就答對） |
| 同一台機器上的其他工作階段互傳訊息 | `ListAgents` 看得到同機器的工作階段，`SendMessage` 直接送；但雲端容器一次只有一個工作階段，實測列表是空的 | 可以：同一台電腦開幾個 Claude Code 對話，彼此看得到、能互傳、能分派（**11/09 實測雙向通過**，一來一回約 1 分鐘） |
| 開新的雲端工作階段並下指令 | 可以：`create_session`＋`send_message`，能指定模型、分支、起始提示；對方做完能回訊 | 桌面版可從任務卡開雲端或本機工作階段；也能用 claude.ai/code 手動開 |
| 本機 ↔ 雲端互傳訊息 | 雲端看不到本機（Windows 資料夾接不上 Remote Control）；只能靠**任務卡**（`spawn_task`）把工作送到本機，和 **git 分支**交接結果。工具說明（11/09）：雲端工作階段**目前不能傳訊息給其他工作階段**，收到的訊息只能在自己的對話紀錄裡回；**11/09 實測更正**：雲端用 Remote 的 `send_message` 可以回傳本機，但第一次會被擋（`elevated_session_untrusted_device`），要使用者在信任裝置上核准一次（核准後該雲端工作階段只限信任裝置使用，不可逆） | **11/09 實測：雙向可通。** 本機 → 雲端直接送；雲端 → 本機要使用者先核准一次（見左欄），本機收到的訊息會標明雲端的 `session_…` ID。 `ListAgents` 列得到帳號下所有雲端工作階段（11/09 列出 38 個同伴，含 cloud、Remote Control、桌面版三類），`SendMessage` 送出時只顯示「未確認已讀」；雲端那邊收到後狀態變成「等待使用者」。列表顯示的是對話標題，不是 `session_…` ID；桌面版的 `list_sessions` 只列本機工作階段 |
| 排程喚醒 | 有（`create_trigger`、`send_later`） | 桌面版有排程任務 |
| GitHub 事件喚醒 | 有（訂閱 PR，CI 紅了會叫醒） | 無 |
| 外部模型 | 沒有 agy；審議席只能用 Claude 不同模型，或等本機 | 有 agy（Gemini、GPT-OSS）、Copilot 雲端代理（`gh agent-task`） |
| 真耳朵、Unity、錄影、授權、合併 | 無 | 有 |
| 錄音分析、Playwright、Node 測試、CI | 有 | 有（要自己裝 Chromium） |

一句話：**雲端能「開別的雲端工作階段並指揮它」，本機能「同機多對話互傳、叫外部模型、碰硬體」；兩邊之間有任務卡（單向：雲端 → 本機）、互傳訊息（雙向，11/09 實測；雲端回傳要使用者先核准一次）和 git（雙向）。**

### 12.2 分工架構（現行，11/09 定稿）

```
使用者（製作人）
 │ 決定方向、選擇題、真耳朵、合併 main
 ├─ 雲端主對話（總控，Fable）────────────────────────────┐
 │   負責：拆工作、寫介面約定、整合、提交推送、審議裁判、盯 CI、寫交接   │
 │   ├─ 子代理（Opus 開發／Sonnet 整理，照檔案切、同輪最多 3 個、可續用）│
 │   ├─ 側工作階段（create_session：長任務、獨立分支，做完回訊；審過合併進工作分支）│
 │   ├─ 排程與 PR 事件（CI 紅了自動醒來修）                          │
 │   └─ 任務卡＋互傳訊息（雙向）─────────────────────────┐   │
 │                                                        ▼   │
 └─ 本機主對話（Opus／Fable）                        接卡開工     │
     負責：真耳朵試玩、Unity、錄影、上傳、合併 PR；叫外部模型當審議席 │
     ├─ 子代理（同機可多對話互傳）                                 │
     ├─ agy（Gemini、GPT-OSS：審議席、翻譯、整理）                   │
     └─ Copilot 雲端代理（自足的 repo 任務，開 PR）                  │
                                                                 │
     git 分支 claude/gracious-bardeen-vwo4rr ◄──── 檔案與結論的雙向通道 ─┘
     （換手前推、接手前拉；結論一律寫進 docs/；試玩數據自動進試玩頁資料庫）
```

**流程一輪**：使用者需求 → 雲端分級（L1～L3）→ 雲端寫規格／約定 → 子代理並行開發 → 稽核或檢查代理 → 修正 → 提交推送、更新試玩頁 → 任務卡交本機 → 本機真耳朵＋外部審議 → 推回 → 雲端裁判、改規格、下一輪。

**誰該在哪邊做**（補 9.2 節）
- 要「指揮另一個長任務又不想塞爆主對話」：雲端開側工作階段（不是子代理），完成回訊再合併。
- 要「三個模型各審一次」：本機 agy；雲端只能 Claude 不同模型。
- 要「半夜自動跑、CI 紅了自己修」：雲端。
- 要「兩個對話邊做邊對話」：本機同機多對話（雲端一容器一對話，做不到）。
- 本機做完一件雲端在等的事：推 git 後**順手 `SendMessage` 一句給雲端工作階段**（說明推了什麼、在哪個提交），雲端下次醒來就看得到，不用使用者轉述，也不必等雲端下次醒來才交接。
- 雲端要回傳本機前，先向使用者要一次信任核准（核准卡片，使用者在信任裝置上按同意；不可逆）；核准後本機就能等雲端主動回報，不必輪詢。
- `ListAgents` 只列對話標題，同題的雲端對話可能不只一個（11/09 就送錯對象），任務卡裡要寫雲端對話的**標題**，不要只寫 `session_…` ID。
