# AI 協作與分工介紹

## 1. 角色

| 角色 | 是誰 | 負責 | 不做 |
|---|---|---|---|
| **製作人／設計決策** | 使用者 | 定方向、選方案、試玩、回饋 | — |
| **主對話（協調者）** | Claude Code 主對話 | 拆工作、寫給代理的任務說明、整合結果、跑測試、提交與推送、發布網頁、更新文件、向使用者報告 | 不在代理工作時改同一個檔案 |
| **開發代理** | Claude 子代理，每次一個任務 | 只改指定的檔案：規則模組＋測試，或畫面層，或一個原型 | 不提交、不推送、不碰別人的檔案 |
| **檢查代理** | 獨立的 Claude 子代理 | 用瀏覽器（Playwright）實際打開原型、程式化試玩、截圖，對照設計文件列出問題 | 不改任何檔案，只回報 |

## 2. 工作規則（寫在 `CLAUDE.md`，每個新對話都會讀到）

1. **不確定先提問**：用選擇題問，附建議選項；有慣例可循的就直接決定。
2. **快要難以移植時先停下來**：說明會綁住什麼、移植要重做多少，讓使用者選。
3. **代理分工**：各部分交給代理；主對話負責整合、提交、報告。
4. **內容限制**：所有內容出自《奧德賽》（含使用者指定參考的電影改編），不出現現代元素。
5. **發想登記**：主線以外的概念都登記在 `docs/design/concepts-overview.md`。

## 3. 一輪的流程

```
使用者提出需求
  → 主對話：不確定的地方用選擇題問清楚
  → 主對話：先把設計寫進文件（設計先於程式）
  → 主對話：提交目前進度，當作代理的共同起點
  → 開發代理 ×N 同時進行（每個只改自己的檔案）
  → 主對話：收報告、轉告相關代理（例如規則新增了欄位）、跑測試、提交
  → 檢查代理：實際打開、試玩、對照設計
  → 修正代理 ×N
  → 主對話：測試、提交、發布、向使用者報告
```

## 4. 為什麼「規則」和「畫面」分開

- **規則檔**：純邏輯，不碰畫面、聲音、輸入裝置，例如 `sim.js`、`rules.js`。
  - 可以用 Node 直接測試，也可以寫「程式玩家」驗證關卡能不能過、會不會太簡單。
  - 之後搬 Unity，只要翻成 C#，對應主線的 `Odyssey.Core`。
- **畫面檔**：每幀把輸入交給規則，再照規則的狀態畫出來，例如 `index.html`。
- **分工上的好處**：規則代理和畫面代理可以同時工作，只要事先講好兩邊的介面。

## 7. 分工路線比較（11/08，依這兩週實際用過的做法）

| 路線 | 怎麼做 | 用在 | 優點 | 缺點 | 實測數字 |
|---|---|---|---|---|---|
| **A. 單一對話迭代** | 一個對話從頭做到尾，使用者回饋就改 | 主線《雙盲洞穴》前期、小修（按鍵配置） | 脈絡完整、不用寫任務說明、小改最快 | 一次只能做一件事；上下文累積後容易出錯、變英文；沒有獨立檢查 | 洞穴 20 多輪回饋；按鍵配置從決定到推送 10 分鐘 |
| **B. 主對話＋開發代理（照檔案切）** | 主對話寫介面約定，規則、聲音、畫面各一個代理同時改各自的檔，主對話整合、測試、提交 | 木馬之夜每一輪、返回主畫面、稽核修正 | 三倍並行；檔案不互踩；規則與畫面分離本來就是為了這個 | 介面要先寫清楚（約定檔）；代理各讀一遍規格很貴；一個代理晚到，其他要等 | 稽核修正三代理各 19～23 萬 token、11～14 分鐘同時跑完；比序列省約 2/3 時間 |
| **C. 開發 → 檢查 → 修正三段** | 開發代理做完，獨立的檢查代理實際打開玩、對照設計列問題，再派修正代理 | 乞丐與比箭 11/04、網頁連作 11/05 | 抓到作者看不到的錯（選單蓋住畫面、大廳直走就贏） | 多一輪時間；檢查代理要能「真的玩」（Playwright、錄音工具） | 兩次檢查各抓到 3～9 個會擋住的錯 |
| **D. 審議會（多席獨立＋裁判）** | 同一題給 N 席各自盲答（不同立場或不同模型），裁判只採信能查證的主張 | 木馬之夜設計審視 11/07 | 找出「測試過了但設計壞了」的問題；分歧本身就是資訊 | 貴（五席 12～14 萬 token 各一份）；同一家模型共用盲點；裁判要自己動手算，不然只是投票 | 五席「最該先改」選了四件不同的事；裁判算出腳步掩護方向反了，五席只有一席真的算過 |
| **E. 稽核代理（只讀、只算、只錄）** | 一個代理不改檔，用 Node 把公式全部算一遍、跑錄音工具，列錯誤清單 | Risset 層稽核 11/07 | 比審議便宜、比測試深；產出直接是修正清單 | 只看得到「有沒有照原理做」，看不到「好不好玩」 | 22 萬 token，15 個錯，其中 2 個聽得出來 |
| **F. 搜尋比較代理** | 一個代理上網查、寫比較表 | 音效工具比較 11/07 | 主對話不用自己翻幾十個網頁 | 數字要再確認（授權門檻抓不到官網原文） | 16 萬 token、25 次搜尋、55 條來源 |
| **G. 雲端／本機分工** | 雲端做「對不對」（規則、測試、錄音分析），本機做「好不好」（真耳朵、Unity、錄影）；只靠 git 分支交接，用任務卡片開本機對話 | 11/07 起 | 各做各擅長的；本機的試玩紀錄直接變雲端的需求 | 來回一次至少半天；喇叭聽不出來這種事雲端量不到，要本機先說 | 第一輪試玩三項聽不出 → 雲端改成 8 項可量的檢查 |
| **H. 多代理工作流（Workflow）** | 用腳本把 N 個代理排成管線，自動分支 | 還沒用 | 可大量並行、可重跑 | 要使用者明確同意；這個專案的規模還不需要 | — |

**什麼事用哪條**
- 小修、文件對齊、提交：A。
- 一輪功能開發（兩個檔以上同時改）：B，必要時接 C。
- 「測試都過了但感覺不對」：先 E（便宜、有數字），數字看不出再 D。
- 要查外部現況：F。
- 任何「好不好聽、好不好玩」：G，雲端不要猜。
- 一輪完整流程的建議順序：設計文件 → B 開發 → E 稽核或 C 檢查 → 修正 → G 本機試玩 → 回到設計文件。

**代理用量的經驗值**（這個專案）
- 讀完規格再動手的開發代理：15～23 萬 token；只讀不改的稽核、審議席：12～22 萬。
- 最貴的不是代理本身，是「每個代理都重讀一次規格」。給代理的說明寫明只讀哪幾節、把介面約定寫成一個小檔讓大家讀同一份，比省模型更有效。
- 主對話的上下文會被代理報告塞滿，所以代理報告的結論要立刻寫進 `docs/`（重啟時曾丟過兩份報告，見檢討第 17 項）。

## 8. 模型選擇（11/08）

這個工作階段的主對話跑 Claude Fable；子代理不指定時沿用主對話的模型，可以指定 Opus、Sonnet、Haiku。

| 角色 | 建議模型 | 理由 |
|---|---|---|
| 主對話（拆工作、寫約定、整合、提交、和使用者對話） | 最強的那一個（目前 Fable） | 脈絡最長、決定最多；錯一個決定比省一點錢貴 |
| 開發代理（規則、聲音、畫面） | 沿用主對話 | 要讀懂規格、寫測試、自己驗證；省不得 |
| 檢查、稽核代理 | 沿用主對話 | 要自己算、自己跑工具；弱模型會「看起來查了」 |
| 審議席 | **刻意混用**：主對話模型的不同立場 ＋ Opus ＋ Sonnet 各一席 | 同一家模型共用盲點，換模型是最便宜的「換腦袋」。11/07 五席裡 Opus 席提出「盲區被稀釋」、Sonnet 席提出「盲區加寬」，都是 Fable 三席沒提的角度 |
| 搜尋比較、文件翻譯、整理清單 | Sonnet 或 Haiku | 工作明確、靠工具不靠推理；Haiku 適合「把 N 份文件的英文找出來」這種機械活 |
| 程式玩家、數值模擬 | 不用模型，寫成 Node 腳本 | 模擬一次幾秒、可重跑；比叫代理「估一下」準 |
| 外部模型 | **11/08 本機確認**：透過 Antigravity CLI（`~/.gemini/bin/agy.exe`，`agy models`）可用的模型有 `gemini-3.8-flash-high／medium／low`、`claude-sonnet-4-6`、`claude-opus-4-6-thinking`、`gpt-oss-120b-medium`；GitHub Copilot 雲端代理（`gh agent-task create -R … -F 簡報.md --base 分支`，本機沒有問答版 CLI）可以當審議席：簡報裡寫明只讀哪幾個檔、答案寫成獨立新檔、不讀其他席，它會自己開分支與 PR（11/08 第一次用，PR andy970627/test1#8，丁席）。11/08 審議席：`gemini-3.8-flash-high`（甲）、`gpt-oss-120b-medium`（乙）、Claude Opus 懷疑者（丙）、Copilot 雲端代理（丁） | 用途（使用者決定）：審議席、搜尋比較與文件翻譯等機械活；不當開發代理（沒有這個工作階段的工具，只能給文字任務再貼回結果）。實測限制（11/08）：列印模式 `-p` 讀不到 stdin、命令列長度塞不下整份規格，要用 `--add-dir <資料夾>` 把題目檔放進工作區讓它自己讀；題目裡要寫明「不要用其他工具」，否則 gpt-oss 連算術題都會去叫指令、在 headless 下被擋成空白回答。第一次用在《大廳復仇》合成版規格審議，原文見 `docs/design/2026-11-08-vengeance-v2-council.md` |

**原則**：主幹用最強模型、把錢花在「決定」上；平行的機械活降級；審議刻意混模型（含外部模型）；能用腳本算的不要用模型猜。

**外部模型進審議會的做法**：同一份題目與檔案清單給外部模型一份（它讀不到這個工作樹，所以題目裡要貼上需要的文件段落），答案存進 `docs/design/` 的審議文件附錄，裁判一樣只採信能查證的主張，並在報告裡註明是哪個模型。
