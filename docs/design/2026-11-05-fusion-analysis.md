# repo 內各遊戲的融合搭配分析

日期：2026-11-05　範圍：repo 所有分支裡的遊戲與遊戲概念（不含入門教材 `ideas/unity-game-dev-101`）

## 1. 盤點：有哪些遊戲

| 代號 | 遊戲 | 在哪裡 | 成熟度 | 技術 |
|---|---|---|---|---|
| **A** | 《雙盲洞穴》獨眼巨人洞穴（主線） | `blind-cave` 等分支；規格到第 33 節 | 高：可玩、有測試、有 WebGL 流程 | Unity 6000.3，規則在 `Odyssey.Core`（C#） |
| **B1** | 《奧吉吉亞：第七年》異常航海 | `blind-cave` 分支 `docs/design/2026-10-10-ogygia-gdd.md` | 中：完整總綱，沒有程式 | 計畫用 Unity |
| **B2** | `odyssey-horror` 迴圈恐怖雛形 | `odyssey-horror` 分支（從別的 repo 匯入） | 低：手電筒、追逐怪、驚嚇點的教學級腳本 | **另一個 Unity 專案，2022.3** |
| **C** | 《門檻上的乞丐》偽裝潛行 | `prototypes/beggar-hall/` | 中：網頁原型、規則有 31 項測試 | 網頁；規則 `sim.js` 可翻 C# |
| **D** | 《伊薩卡比箭》 | `prototypes/bow-contest/` | 中：網頁原型、17 項測試 | 網頁；規則 `rules.js` 可翻 C# |
| 小 | 斯庫拉與卡律布狄斯、海妖、聖牛、岸邊的抉擇、羊肚底下 | 各設計文件 | 只有發想（岸邊抉擇在主線規格第 20 節） | — |

**B1 和 B2 是同一個概念的兩個版本**（困在卡呂普索的島、海神用異常把你送回去）。B2 比較早、比較粗，而且有違反專案規則的地方（見第 5 節），融合時應該合併成一個，以 B1 為準。

## 2. 依《奧德賽》時間線排列

```
特洛伊 → [A 獨眼巨人洞穴，第 9 卷] → 岸邊的抉擇
      → （海妖、斯庫拉、聖牛，第 12 卷）→ 同伴全死
      → [B 奧吉吉亞七年，第 5 卷] → 木筏漂到伊薩卡
      → [C 門檻上的乞丐，第 17～20 卷] → [D 比箭，第 21 卷] → 屠殺（第 22 卷）
```

剛好一條沒有重疊的時間線，各遊戲各占一段。這是融合最大的本錢。

## 3. 兩兩搭配評估

| 搭配 | 適合度 | 連結點 | 衝突或風險 |
|---|---|---|---|
| **A → B** | ★★★★☆ | **因果相連**：在洞外喊出名字或射箭，才招來波塞頓的怒氣；而 B 的整個迴圈就是那份怒氣。A 的岸邊抉擇可以決定 B 的「怒氣等級」（巨浪多快、異常多細微） | 原典裡到奧吉吉亞時同伴已經全死，A 救出幾個人不能直接帶過去。可以改成 B 的異常：「礁石上站著你沒救出來的同伴」 |
| **B → C** | ★★★☆☆ | 木筏漂到伊薩卡就接 C 的豬倌小屋。B 花掉的年數可以影響 C：年數越多，求婚者越囂張（會丟東西的人更多）、潘妮洛普離改嫁越近（時間限制）、阿爾戈斯越老 | **重複**：B1 的最終關「伊薩卡大廳找異常」（阿爾戈斯、神像、弓、斧頭、豬倌）和 C 的大廳幾乎是同一批東西。融合就要刪掉 B1 的最終關，讓 B 停在上岸 |
| **C → D** | ★★★★★ | 已經設計好：D 就是 C 的第 8 段；C 記的「帳」越多，D 拉弓越穩 | 幾乎沒有。D 可以同時保留成獨立的網頁小品 |
| **A ↔ C**（同樣是潛行） | ★★★★☆ | **互為反面**：A 躲在黑暗裡「別被聽見」，C 站在火光下「被看見但別被看穿」。主角的變化：A 傲慢地喊出名字，C 得把名字吞下去 | 都是潛行，玩久可能覺得重複；要靠感官不同（聽 vs 被看）、場景亮暗相反來拉開差距 |
| **A ↔ D**（都有弓） | ★★★★☆ | **宙斯法則**（主線第 31 節：不從暗處出手）：A 在岸邊射睡著的巨人是偷襲；D 在大廳當眾射出是正面出手。拉弓、手抖的手感可以共用 | 主線的弓是偵察與引開用，D 的弓是精準射擊，兩種手感要分開調 |
| **A ↔ C**（主客之誼） | ★★★★★ | 巨人吃掉他的客人；求婚者羞辱乞丐客人。兩個段落都是「違反宙斯的待客法則」，可以當整部作品的主題 | — |
| **小品 → B** | ★★★★☆ | 斯庫拉、海妖、聖牛本來就是 B1 的特殊航段 | — |
| **羊肚底下 → A** | ★☆☆☆☆ | 同一個場景 | 主線已經用「天光引羊」取代它，再放回去會打架；不建議融合 |

## 4. 整體來看

**適合融合的理由**
1. **時間線不重疊**，自然能排成章節。
2. **共同主題很清楚**，三條線貫穿四款：
   - 宙斯的待客法則：巨人和求婚者都違反它，你自己守不守得住
   - 名字：在洞外喊出名字，回到家卻要藏起名字
   - 薛西弗斯式的徒勞：一夜又一夜、一年又一年、一次又一次被羞辱
3. **感官三部曲**：A 聽（看不見）→ B 看（找出不對勁）→ C 被看（不能被看穿）→ D 看準（一箭穿過 12 孔）。每章換一種感官，不會玩成同一款遊戲。
4. **情緒弧線**：恐怖（洞穴）→ 不安（海上）→ 屈辱的緊繃（大廳）→ 宣洩（比箭）。電影版的結局偏蒼涼，最後一章可以選要宣洩還是蒼涼。
5. **跨章的累積**都已經有雛形，可以串起來：
   - A 的岸邊抉擇 → 波塞頓的怒氣
   - B 的年數 → C 的難度與時限
   - C 的帳 → D 的穩定度

**不適合硬融合的地方**
1. **規模**：四款各自都是完整的遊戲，合成一款會變成很大的專案。
2. **操作衝突**：同一個按鍵在各款意思不同，融合就要統一：

   | 按鍵 | A 洞穴 | C 乞丐 | D 比箭 | B2 |
   |---|---|---|---|---|
   | 空白鍵 | 甩投石索／拍手 | 笨拙地閃 | 拉弓（備用） | — |
   | F | — | 捶胸 | — | 手電筒 |
   | Shift | 跑 | 站直 | — | — |
   | Q | — | 示意 | — | — |
   | E | 互動 | 互動 | — | 互動 |

3. **技術散在三處**：主線是 Unity 6000.3；B2 是另一個 Unity 2022.3 專案；C 和 D 是網頁。C 和 D 的規則已經是可翻成 C# 的獨立模組，搬進主線專案不會綁死。B2 只有教學級腳本，不值得遷移版本，直接以 B1 重寫比較省。
4. **內容規則不一致**（見第 5 節）。

## 5. 要先處理的衝突

| 衝突 | 內容 | 建議 |
|---|---|---|
| B2 違反內容限制 | **手電筒**（現代物品）；異常裡有忘憂果、喀耳刻、冥府，但 B1 規定只用電影演過的內容 | 以 B1 為準；手電筒改成油燈或火把 |
| 電影 vs 原典 | B1 只用電影內容；C 混用原典（伊羅斯、洗腳）和電影（盲眼豬倌、神像相認）；A 以原典為主、參考電影 | **已決定（11/05）**：全系列以電影為主、原典補充、可適度改編，並標【電影】【原典】【改編】（見 `CLAUDE.md`）。B1 的「只用電影」放寬成這條；A 的規格之後動到時補標出處 |
| B1 最終關和 C 重複 | 都在伊薩卡大廳認東西 | 融合時刪掉 B1 的最終關 |
| 結局 | B1 有「永生」「布織完了」等多個結局；A 有岸邊三選一；D 是屠殺；電影是交出王位、往西航行 | 融合版需要一條總結局線 |

## 6. 建議

**做成「連作」：四章各自能單獨玩，再加一份可選的跨章存檔**，而不是一開始就合成一款大遊戲。

| 方案 | 說明 | 優點 | 缺點 |
|---|---|---|---|
| **連作（建議）** | 每章是完整的小遊戲，可以單獨發布（網頁或 itch.io）；有跨章存檔時，前一章的結果影響下一章 | 每章做完就能發表；不必等全部完成；主線不受影響 | 跨章的影響要設計得夠有感 |
| 一款大遊戲 | 一個 Unity 專案、一條流程從洞穴玩到比箭 | 敘事最完整 | 規模最大、最慢看到成果，任何一章卡住全部卡住 |
| 不融合 | 各做各的 | 最簡單 | 浪費了第 4 節那些現成的連結 |

**建議順序**
1. 主線 A 先做完，它最成熟。
2. 接著做 C＋D 當第二章，原型已經有，規則翻成 C# 放進主線專案。
3. B 放最後。它最大，異常也最吃美術；開工前先合併 B1 和 B2。
4. 先定統一的按鍵配置（第 4 節）。內容規則已定（第 5 節）。
